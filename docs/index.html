AES-ECB mode is unsafe

ECB always maps the same 16-byte plaintext block to the same ciphertext block. That leaks patterns and equality, while the absence of authentication lets attackers rearrange ciphertext undetected.

Four demonstrations make those failures visible, then apply the same attack to AES-GCM to show the control that stops it.

The demonstrations use real AES through the Web Crypto API. They run entirely in this page, and no entered data leaves your browser. View the source and verification tests on GitHub →

Purpose and safe scope

These demos help engineers recognize, prevent, and fix ECB misuse. Each target is a self-contained browser simulation. Use these techniques only on systems you own or are explicitly authorized to assess.

How the weakness arises

AES processes 16-byte blocks. ECB encrypts each block independently under one key, with no IV, nonce, or dependency on another block: Cᵢ = E_K(Pᵢ). NIST SP 800-38A §6.1 notes that a plaintext block always maps to the same ciphertext block under a given key and advises against ECB when that property is undesirable. Because a block cipher under a fixed key is a permutation, equal ciphertext blocks also reveal equal plaintext blocks. ECB therefore behaves like a fixed codebook.

NIST has also announced that its planned revision of SP 800-38A will limit ECB approval to uses specifically allowed by other NIST guidance.

The difference from a safe mode is entirely in what feeds each block encryption. ECB feeds it the plaintext block alone, so two equal plaintext blocks take the same path to the same ciphertext. CBC XORs each block with the previous ciphertext, and the first block with an IV that must be fresh and unpredictable for every message; GCM never encrypts the plaintext directly — it encrypts a per-message nonce-plus-counter and XORs the result in, then authenticates. In both cases the per-message value is doing the work: hold the IV or nonce constant and the repeat comes straight back.

Why determinism breaks confidentiality

A mode should be indistinguishable under chosen-plaintext attack (IND-CPA): submit two equal-length messages, receive the encryption of one chosen at random, and you should not guess which better than a coin flip. Consider two 2-block messages — one is A×16 ∥ A×16 (identical blocks), the other A×16 ∥ B×16 (distinct). Answer "first" if the two ciphertext blocks are equal. You are right every time, because ECB's determinism makes C₁ = C₂ exactly when P₁ = P₂. Advantage 1 — the maximum. A stronger key does not change this; the break is in the mode.

A passive observer needs repeated blocks to see this pattern. The IND-CPA break does not: an encryption oracle lets an attacker encrypt either one-block candidate and compare it with the challenge. “It is only one block” may prevent a passive collision, but it does not make ECB IND-CPA secure. For key wrapping, NIST specifies dedicated modes in SP 800-38F rather than raw ECB.

Two root causes, four vectors

These four vectors reduce to two properties. Determinism drives the three confidentiality attacks. Cut-and-paste needs determinism to make blocks portable and missing authentication to let the splice pass unnoticed.

Vector 1 — Pattern & structure leakage

Identical plaintext regions become identical ciphertext regions. Uniform image backgrounds, repeated record layouts, and fixed protocol headers all survive encryption as visible structure. Encrypt a structured bitmap and its outline persists through ECB — but dissolves under CBC and GCM.

Vector 2 — Equality & frequency inference

Determinism preserves equality across every row of a dataset encrypted under the same key: two ciphertext blocks are equal iff the plaintext blocks were. That alone lets an attacker cluster records by identical ciphertext with no decryption — the mechanism behind Adobe's 2013 breach, where 152,982,479 password records were ECB-encrypted (not hashed) without a per-user salt, so identical passwords produced byte-identical ciphertext.

The leak is not specific to passwords, and clustering is not the end of it. Equality plus frequency is often enough to name the values: Naveed, Kamara & Wright (ACM CCS 2015) recovered plaintext attributes from deterministically encrypted database columns using frequency analysis against publicly available auxiliary data, evaluated on real hospital inpatient records (the HCUP National Inpatient Sample) — no key, no decryption, no oracle. Their target was deterministic encryption inside encrypted-database systems rather than ECB specifically; the shared property is determinism, which is exactly what ECB has.

Cluster users by ciphertext — no decryption

Passwords need a different fix. AEAD would stop ciphertext clustering, but anyone who obtains the encryption key could still recover every password. NIST SP 800-63B-4 §3.1.1.2 requires salted password hashing, a cost factor that is as high as practical, and a salt of at least 32 bits. It points to approved schemes in the latest SP 800-132 or updated NIST guidance. Store the scheme and cost with each verifier so they can be raised over time.

Vector 3 — Chosen-plaintext byte-at-a-time recovery

When a service computes ECB(attacker_input ∥ secret) — say, an endpoint that appends a session token to whatever you submit before encrypting — you can recover the secret one byte at a time, from ciphertext alone. Send just enough filler to push one unknown byte into the last slot of a block, capture that block as the target, then try all 256 values in that slot until the ciphertext matches. Shift down one byte and repeat (Cryptopals Set 2 Challenge 12).

Count the queries carefully, because the obvious figure is short by one per position. Each position costs one query to capture the target block plus at most 256 to find the byte, so a secret of L bytes costs at most 257 × L queries, and at most 34 more on top to detect the block size and the secret's length. The average is about 129 × L, since the search stops at the matching candidate, and printable ASCII lands lower still. The 48-byte default below takes exactly 4,588 queries against a 12,370 worst case — the same number on every run, because the count depends on the secret's byte values and not on the key. The demo prints its own count so you can check it against both figures.

Vector 4 — Block malleability / cut-and-paste

Because ECB's codebook map is fixed and position-independent, a ciphertext block decrypts to the same plaintext block wherever it is placed — so ciphertext blocks are portable units — and with no authentication tag, nothing detects that one has been moved. If you can get chosen plaintext encrypted under the target key — for example by controlling your own account's email field — you can splice a block that decrypts to role=admin onto an otherwise legitimate token, and the server accepts it: no decryption error, no signature to forge (Cryptopals Set 2 Challenge 13).

Detecting ECB

Two independent angles, because the ciphertext-only test cannot see a codebase and the source-only test cannot see a black box.

  • Black-box (ciphertext or oracle access): split the ciphertext into fixed-size blocks and look for duplicates — exactly what the block playground above does. Against a live oracle, submit repeated blocks and check whether any two outputs match.
  • White-box (source or configuration review): search for MODE_ECB, modes.ECB(, /ECB/, or an unqualified Cipher.getInstance("AES"). Oracle's current JCA reference guide recommends specifying the full transformation because SunJCE and SunPKCS11 default many symmetric ciphers to ECB with PKCS5Padding.

Read the black-box result carefully, in both directions. A repeat is not necessary: the passive test misses ECB entirely when the sampled plaintext happens to contain no repeated block, which is why the active oracle variant — where you supply the repeats yourself — is the more reliable of the two. Nor is a repeat quite sufficient. Within a single message it effectively is, since a correctly-IV'd chaining mode would have to collide by chance at around 2−128 per pair, so ECB is the overwhelmingly likely cause. Across a corpus of separate records it is not: CBC under a constant IV, or CTR under a reused nonce, produces the very same signature without being block-independent at all — and a constant IV is a common real defect, found in 1,932 of the Android apps in the study cited below. Treat a repeat as strong evidence of determinism, then confirm the mode.

The fix — authenticated encryption

Use AEAD with a fresh nonce per message: AES-GCM or ChaCha20-Poly1305. The nonce breaks the determinism Vectors 1–3 depend on, and the authentication tag — verified before any plaintext is trusted — closes Vector 4: a tampered or spliced ciphertext fails verification instead of silently decrypting to attacker-chosen content.

Note what this does and does not establish. It shows that a spliced token fails tag verification and returns nothing — that is Vector 4 closed. It does not show that GCM is safe under nonce reuse, which is a separate property and the subject of the next section.

If AEAD genuinely is not available, CBC with a fresh unpredictable IV per message — or CTR with a counter block that is never reused under the same key — plus a separately computed MAC (encrypt-then-MAC, verified before decryption) restores confidentiality and integrity. It is strictly more to get wrong than using an AEAD mode directly.

Switching the mode only protects data written from now on. Anything already stored under ECB keeps leaking until it is rewritten: decrypt it with the old ECB key and re-encrypt under the new AEAD scheme with fresh per-message nonces, as a one-time migration. Rotate the key at the same time so the retired ECB key can be destroyed and old ciphertext cannot be revived.

Residual risk after switching to GCM

GCM defeats all four vectors but adds a failure mode of its own: reusing a (key, nonce) pair breaks confidentiality and leaks the authentication key, which lets the tag be forged. An Internet-wide scan (Böck et al., USENIX WOOT 2016) found 184 HTTPS servers repeating AES-GCM nonces, fully breaking authenticity of those connections.

The requirement is uniqueness, not randomness. SP 800-38D §8 states it as a probability bound: the encryption function "shall" never be invoked "with the same IV and the same key on two (or more) distinct sets of input data" with probability greater than 2−32. §8.2 gives two approved ways to get there, and an implementation picks one per key:

  • Deterministic (§8.2.1) — a fixed field identifying the device or context, plus an invocation field such as a counter. A 96-bit deterministic IV is exempt from §8.3's global 232 cap, but the counter still must not repeat; rekey before its invocation field is exhausted.
  • RBG-based (§8.2.2) — at least 96 random bits from an approved RBG. This is what the demos above use, and what crypto.getRandomValues gives you.

Choosing the random construction buys simplicity and costs a ceiling: §8.3 caps total invocations per key at 232. The same global cap applies when the deterministic construction uses IV lengths other than 96 bits. These are operational limits for a rekey schedule, not properties GCM enforces for every caller.

Standards status, September 2026. SP 800-38D remains NIST's published GCM recommendation. NIST's current revision proposal would remove authentication tags shorter than 96 bits; it is a pre-draft call for comments, not a replacement standard. The demos use Web Crypto's 128-bit tag.

What to remember

The four failures here follow from deterministic block encryption, missing authentication, or both. Replace ECB with authenticated encryption and a nonce that is unique per key. For stored passwords, use password hashing rather than reversible encryption.
