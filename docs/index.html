Cryptography / Failure analysis

AES-ECB mode is unsafe

Electronic Codebook (ECB) encrypts every block independently under the same key, with no randomization and no dependency between blocks. That determinism alone breaks confidentiality outright: ECB fails the standard IND-CPA definition with adversary advantage 1, regardless of key size. A second property — no authentication — means nothing detects a ciphertext that has been altered or reassembled, which is what turns the same determinism into forgery.

Scope — educational / defensive use

These demos exist to help you detect, prevent, and fix ECB misuse. Each attack runs against a self-contained, in-page oracle — there is no network and no third-party system. Every weakness is paired with its mitigation. Do not point these techniques at any system you do not own or are not authorized to test.

The mechanism

A message is split into fixed-size blocks — 16 bytes for AES — and each block is encrypted independently under the same key, with no IV, no nonce, and no dependency on any other block: Cᵢ = E_K(Pᵢ). NIST defines ECB in SP 800-38A, which states the property plainly: "under a given key, any given plaintext block always gets encrypted to the same ciphertext block," and "if this property is undesirable in a particular application, the ECB mode should not be used" (§6.1). The detection consequence follows from that property rather than from NIST: a block cipher under a fixed key is a permutation, so equal ciphertext blocks imply equal plaintext blocks and vice versa — inspecting any two ciphertext blocks reveals whether the corresponding plaintext blocks were equal. ECB behaves like a fixed lookup table — a codebook.

The difference from a safe mode is entirely in what feeds each block encryption. ECB feeds it the plaintext block alone, so two equal plaintext blocks take the same path to the same ciphertext. CBC first XORs each block with the previous ciphertext (the first with a random IV); GCM never encrypts the plaintext directly — it encrypts a per-message nonce-plus-counter and XORs the result in, then authenticates.

Why determinism breaks confidentiality

A mode should be indistinguishable under chosen-plaintext attack (IND-CPA): submit two equal-length messages, receive the encryption of one chosen at random, and you should not guess which better than a coin flip. Consider two 2-block messages — one is A×16 ∥ A×16 (identical blocks), the other A×16 ∥ B×16 (distinct). Answer "first" if the two ciphertext blocks are equal. You are right every time, because ECB's determinism makes C₁ = C₂ exactly when P₁ = P₂. Advantage 1 — the maximum. A stronger key does not change this; the break is in the mode.

Where that argument stops: it needs at least two blocks that can repeat. A single full block that is never repeated under its key has nothing to collide with, so this particular break does not apply to it. That boundary is inference from ECB's own determinism property, not a carve-out NIST makes — SP 800-38A states no exception, and the modes NIST actually approves for wrapping a key are the dedicated ones in SP 800-38F (KW, KWP, TKW), not raw ECB. Treat "it's only one block" as a claim to verify, not a licence.

Two root causes, four vectors

Every vector traces back to these two root causes and to no third. Determinism alone drives the three confidentiality attacks. The cut-and-paste forgery needs both: determinism is what makes a ciphertext block decrypt to the same plaintext block wherever it is placed, and the missing authentication is what lets the moved block go unnoticed.

Vector 1 — Pattern & structure leakage

Identical plaintext regions become identical ciphertext regions. Uniform image backgrounds, repeated record layouts, and fixed protocol headers all survive encryption as visible structure. Encrypt a structured bitmap and its outline persists through ECB — but dissolves under CBC and GCM.

Vector 2 — Equality & frequency inference

Determinism preserves equality across every row of a dataset encrypted under the same key: two ciphertext blocks are equal iff the plaintext blocks were. That alone lets an attacker cluster records by identical ciphertext with no decryption — the mechanism behind Adobe's 2013 breach, where ~153 million password records were ECB-encrypted (not hashed) without a per-user salt, so identical passwords produced byte-identical ciphertext.

The leak is not specific to passwords, and clustering is not the end of it. Equality plus frequency is often enough to name the values: Naveed, Kamara & Wright (ACM CCS 2015) recovered plaintext attributes from deterministically encrypted database columns using frequency analysis against publicly available auxiliary data, evaluated on real hospital inpatient records (the HCUP National Inpatient Sample) — no key, no decryption, no oracle. Their target was deterministic encryption inside encrypted-database systems rather than ECB specifically; the shared property is determinism, which is exactly what ECB has.

The fix for this one is not a better cipher mode. Switching Adobe's storage to AES-GCM would have stopped the clustering and still been the wrong design: an encrypted password is recoverable by anyone who obtains the key. Passwords should not be encrypted at all. NIST SP 800-63B-4 §3.1.1.2 requires that "passwords SHALL be salted and hashed using a suitable password hashing scheme," with a salt of at least 32 bits. In current practice that means a memory-hard scheme — Argon2id, scrypt, or bcrypt — with the cost set as high as the verifier can bear; that is established practice rather than a specific algorithm NIST names in that section. The AEAD fix below addresses the other three vectors, not password storage.

Vector 3 — Chosen-plaintext byte-at-a-time recovery

When a service computes ECB(attacker_input ∥ secret) — say, an endpoint that appends a session token to whatever you submit before encrypting — you can recover the secret one byte at a time, from ciphertext alone. For a secret of L bytes the cost is at most 256 × L queries — one pass through the byte range per position — and about 128 × L on average, since the search stops at the matching candidate. Printable ASCII lands lower still: the 48-byte default below typically falls in roughly 4,600 queries against a 12,288 worst case, and the demo reports its own count so you can check. Send just enough filler to push one unknown byte into the last slot of a block, capture that block as the target, then try all 256 values in that slot until the ciphertext matches. Shift down one byte and repeat.

Vector 4 — Block malleability / cut-and-paste

Because ECB's codebook map is fixed and position-independent, a ciphertext block decrypts to the same plaintext block wherever it is placed — so ciphertext blocks are portable units — and with no authentication tag, nothing detects that one has been moved. If you can get chosen plaintext encrypted under the target key — for example by controlling your own account's email field — you can splice a block that decrypts to role=admin onto an otherwise legitimate token, and the server accepts it: no decryption error, no signature to forge. Detecting ECB

Two independent angles, because the ciphertext-only test cannot see a codebase and the source-only test cannot see a black box.

  • Black-box (ciphertext or oracle access): split the ciphertext into fixed-size blocks and look for duplicates — exactly what the block playground above does. Against a live oracle, submit repeated blocks and check whether any two outputs match.
  • White-box (source / config review): ECB is frequently a library default, not a choice. Grep for MODE_ECB, modes.ECB(, /ECB/, or an unqualified Cipher.getInstance("AES"). That last one names no mode, so the provider picks one: Oracle's JCA reference guide states that "the SunJCE and SunPKCS11 providers use ECB as the default mode, and PKCS5Padding as the default padding for many symmetric ciphers," and the BouncyCastle provider behind most of the Android findings below did the same. The JCA itself defines no default — which is exactly why the call slips through review, and why it is the highest-yield single check.

A repeated ciphertext block is sufficient evidence of deterministic, block-independent encryption (ECB is the overwhelmingly likely cause) but not necessary: the passive test misses ECB when the sampled plaintext has no repeated block, which is why the active oracle variant is more reliable.

The fix — authenticated encryption

Use AEAD with a fresh nonce per message: AES-GCM or ChaCha20-Poly1305. The nonce breaks the determinism Vectors 1–3 depend on, and the authentication tag — verified before any plaintext is trusted — closes Vector 4: a tampered or spliced ciphertext fails verification instead of silently decrypting to attacker-chosen content.

If AEAD genuinely is not available, CBC with a fresh unpredictable IV per message — or CTR with a counter block that is never reused under the same key — plus a separately computed MAC (encrypt-then-MAC, verified before decryption) restores confidentiality and integrity. It is strictly more to get wrong than using an AEAD mode directly.

Switching the mode only protects data written from now on. Anything already stored under ECB keeps leaking until it is rewritten: decrypt it with the old ECB key and re-encrypt under the new AEAD scheme with fresh per-message nonces, as a one-time migration. Rotate the key at the same time so the retired ECB key can be destroyed and old ciphertext cannot be revived.

Residual risk after switching to GCM

GCM defeats all four vectors but adds a failure mode of its own: reusing a (key, nonce) pair breaks confidentiality and leaks the authentication key, which lets the tag be forged. An Internet-wide scan (Böck et al., USENIX WOOT 2016) found 184 HTTPS servers repeating AES-GCM nonces, fully breaking authenticity of those connections.

The requirement is uniqueness, not randomness. SP 800-38D §8 states it as a probability bound: the encryption function "shall" never be invoked "with the same IV and the same key on two (or more) distinct sets of input data" with probability greater than 2−32. §8.2 gives two approved ways to get there, and an implementation picks one per key:

  • Deterministic (§8.2.1) — a fixed field identifying the device or context, plus an invocation field such as a counter. With 96-bit IVs this is the only construction NIST places no invocation ceiling on.
  • RBG-based (§8.2.2) — at least 96 random bits from an approved RBG. This is what the demos above use, and what crypto.getRandomValues gives you.

Choosing the random construction buys simplicity and costs a ceiling: §8.3 caps total invocations per key at 232 for any implementation not using 96-bit deterministic IVs. That is a real operational limit for a long-lived key on a busy service, and it is the sort of thing a rekey schedule has to account for rather than discover. Either way the property must be preserved by every caller — it is not automatic just because the mode is GCM.

What to remember

ECB has exactly two root causes — deterministic, position-independent block encryption and no authentication — and every attack here follows from one or both. The fix is authenticated encryption with a nonce that is unique per key, not a patch to ECB itself; for stored passwords the fix is not encryption at all.
